# 実装指示書：Unsaid Board / 場温計

## 0. これは何か（コーディングエージェントへ）

あなたは**3.5時間・開発者1人・ハッカソン**という制約下で、動くデモを完成させるための実装を行う。
採点は「技術力・発想力・独自性・面白さ・プレゼン」。**勝敗はライブ3分デモの完成度で決まる。**
よって本指示書の最優先事項は「**早い段階で画面に映るものを作り、それを毎回確実に再現できること**」である。

以下の制約を絶対に守ること。違反は失敗に直結する。

- **過剰設計をしない。** プラグイン機構・抽象基底クラス・汎用フレームワークを作らない。要るのは「1つのイベント型」と「それを吐く関数」だけ。
- **ビルド順序を勝手に変えない。** 可視化を最初にデモソースで貫通させる（§5）。実入力検知は後から乗せる第2ソース。
- **スコープを勝手に広げない。** §7 の Non-Goals に挙げたものは作らない。特に AI 聴衆（§6.3）は**カット可能な stretch**であり、コア完成前に着手しない。
- **不明点で止まらない。** 仕様の空白は本指示書の精神（デモ優先・薄い抽象化・床を高く）に沿って最小実装で埋め、`// ASSUMPTION:` コメントを残して進める。

## 1. プロダクト概要（コンセプト）

オンライン会議・授業では、沈黙が「合意」なのか「迷い」なのか分からない。
参加者は言いづらい意見や質問を入力欄に**書くが、必ずしも送信しない**。

**場温計**は、書いて消した内容・入力停止・未送信などを分析し、個人を特定せずに
「不安 / 反論 / 質問 / 納得」の**温度**としてファシリテーターに可視化する。
ファシリテーターは AI 提案（「今、反論が高まっています。匿名で懸念を集めましょう」）を受け取り、
沈黙に埋もれた声を拾える。

**キーメッセージ（プレゼン冒頭）：** 「会議の沈黙は、合意とは限らない。」

**デモの山場（最重要）：** 表面のチャット（送信済み）は穏やかなのに、
場温計の「反論」だけが赤く上昇していく**矛盾の瞬間**を見せる。

## 3. アーキテクチャの核：1つのイベント型に抽象化する

入力ソースが何であれ（実ユーザー / デモデータ / AI聴衆）、**全ソースが同じ1種類のイベントを吐く**。
可視化・集計・ファシリテーター画面は**ソースを一切知らない（source-agnostic）**。これが設計の継ぎ目（seam）。

```ts
// src/lib/events.ts
import { z } from 'zod';

export const Category = z.enum(['不安', '反論', '質問', '納得']);
export const Kind = z.enum(['hesitation', 'deleted', 'sent']);
//  hesitation = 入力して止まった / ためらった
//  deleted    = 書いたが消した（未送信の声 = このアプリの主役）
//  sent       = 実際に送信された（= 表面に見えるチャット）

export const SignalEvent = z.object({
  participantId: z.string(),          // 匿名ID（個人特定はしない。表示にも出さない）
  kind: Kind,
  category: Category.optional(),       // sent でも分類してよいが、主役は deleted/hesitation
  intensity: z.number().min(0).max(1), // 0..1。温度上昇量
  text: z.string().optional(),         // sent のみ表示に使う。deleted の本文は表示しない
  t: z.number()                        // epoch ms
});
export type SignalEvent = z.infer<typeof SignalEvent>;
```

**ソースごとの役割（同じ型を吐くだけ）：**

| ソース | 役割 | LLM を叩くか |
|--------|------|-------------|
| デモソース（§6.1） | 事前分類済みの背景ストリームを**ローカル再生**。デモの大部分を担う | **叩かない（焼き込み済み）** |
| 実入力ソース（§6.2） | プレゼンターが今打つ「1通」を検知 → 分類 → emit | **この1通だけライブで叩く** |
| AI聴衆（§6.3） | 同じ interface の裏に置く stretch。**カット可** | （stretch） |

> 設計意図：背景まで本番で LLM に投げると遅延・失敗が山場を壊す。
> **ライブ AI は「今打った1通」だけ**にし、それを「これは本物のリアルタイム分類です」とプレゼンで明示する。

## 4. 温度モデル（場温計のロジック）

`src/lib/thermo.ts` に、ソース非依存の集計を実装する。

- カテゴリごとに温度 `temp(C) ∈ [0,100]` を持つ。
- 各イベントは該当カテゴリに熱を加える：`heat += intensity * SCALE`。
- **時間経過で指数減衰**（沈黙＝冷却）：`temp(C, now) = Σ_e intensity_e * SCALE * exp(-(now - t_e)/τ)`、`τ ≈ 45s`、`SCALE ≈ 60`、上限100でクリップ。
    - これにより「時間」要素が機能から自然に出る。新しい声が来ないと温度は下がる。
- 表示色：温度で blue(冷)→amber→red(熱) に補間（Tailwind の色 + inline style の HSL 補間で可）。
- **`requestAnimationFrame` か `setInterval(250ms)` で再描画**し、減衰が「ぬるっと」動いて見えるようにする（CV が動いて見える＝面白さ点）。

ファシリテーター提案（`src/lib/suggestions.ts`、**ルールベースで堅牢に**）：
- あるカテゴリが閾値（例 70）を**上抜け**したら提案を1つ発火。
    - 反論 > 70 → 「反論の温度が上がっています。匿名で懸念を集めましょう。」
    - 不安 > 70 → 「不安が高まっています。一度立ち止まって確認しませんか？」
    - 質問 > 70 → 「質問が溜まっています。Q&Aの時間を取りましょう。」
- 連続発火を防ぐためカテゴリごとにクールダウン（例 20s）。
- **LLM は使わない**（堅牢性優先）。余裕があれば文面だけ LLM で言い換える stretch にしてよいが、フォールバックのテンプレ文を必ず残す。

## 5. ビルド順序（この順で作る・各チェックポイントで「動く」こと）

| 時間目安 | ステップ | 完了の定義（必ず満たす） |
|---------|---------|------------------------|
| 0:00–0:20 | 環境確認・OpenAI キー・デプロイ or ローカル画面共有の経路を固定 | `pnpm dev` で起動し、Supabase 接続が通る |
| 0:20–1:15 | **§6.1 デモソース → §4 温度モデル → ファシリテーター画面** を貫通 | **この時点で「動くデモ」が完成**。背景ストリームで温度バーが上下する |
| 1:15–2:00 | **§6.2 実入力ソース**を同じ stream に追加（検知→分類route→emit） | 別タブで打って消すと、ファシリテーター画面の温度が動く |

## 6. ソース別の実装詳細

### 6.1 デモソース（最初に作る・コアの主役）

`src/lib/sources/demoSource.ts`

- **タイムライン化された SignalEvent 配列**を持ち、`start(emit)` で `t` 順に `setTimeout` 発火させる。
- **完全にローカル**で再生する。**Supabase Realtime を経由しない**（会場 Wi-Fi / Realtime が落ちてもデモは完走する）。
- イベントは**事前にカテゴリを焼き込む**（ライブ LLM を通さない）。
- ループ再生 or `reset()` でデモを何度でも頭から流せるようにする。
- 台本（矛盾の瞬間を仕込む。下は例。微調整可）：
    - `t=0..15s`：`sent` で穏やかな同意を数件（"なるほど" "了解です" "いいと思います"）→ 表面チャットは平和。`納得` がやや上昇。
    - `t=10s` 以降：`deleted` / `hesitation` の `反論` イベントを徐々に増やす（本文は表示しない）→ **`反論` 温度が静かに上昇**。
    - `t≈30s`：`反論` が閾値を上抜け → 赤く点灯 → §4 の提案が発火。
    - これが「表面は合意、裏は反論」の**矛盾の瞬間**。

### 6.2 実入力ソース（プレゼンターの「1通」用・第2ソース）

参加者画面 `src/routes/room/[id]/+page.svelte` の入力欄に検知を仕込む。

- 検知トリガー（精度より**デモで確実に発火すること**を優先）：
    - `deleted`：一定時間（例 1.2s）入力が止まった後に**入力長が大きく減った**、または `blur` 時に未送信テキストがある。
    - `hesitation`：入力 → 一定時間停止 → 再開、のリズム。または削除キーの連打。
    - `sent`：Enter / 送信ボタン。
- **deleted/hesitation の本文はサーバーに送ってよいが、分類後すぐ破棄し、画面・DB に本文を残さない**（プライバシー設計。デモでも口頭で明示する）。
- 検知したら `/api/classify` に投げて category/intensity を得て（§6.4）、SignalEvent を emit。
- 実参加者は **Supabase Realtime チャンネル**経由でファシリテーター画面に届ける（複数人が来てもよい設計だが、デモはプレゼンター自身の1タブで十分）。

### 6.3 AI聴衆（STRETCH・コア完成までは着手しない）

- 同じ `SignalEvent` を吐く `src/lib/sources/aiAudience.ts` を**interface だけ**用意する（中身は空 or 簡単なスタブ）。
- 実装は時間が余ったときのみ。間に合わなければ**「設計済み・未実装」と口頭で言うだけ**で発想力点は拾える。**実装を約束しない。**

### 6.4 分類 API route（ライブの1通だけ）

`src/routes/api/classify/+server.ts`

- OpenAI SDK で短文を1回分類。**出力を Zod で検証**し、失敗時はデフォルト（category 推定不能なら `不安`, intensity 0.5）にフォールバック。
- プロンプト（system）例：

```
あなたは会議の未送信テキストを分類する。
入力文を読み、{category, intensity} の JSON のみを返す。前置き・マークダウン禁止。
category は "不安"|"反論"|"質問"|"納得" のいずれか。
intensity は感情の強さ 0.0〜1.0。
本文は分類後に破棄され、保存されない。
```

- `response_format` で JSON を強制できるならする。できなければ受信後に ```json フェンスを除去してパース。
- **タイムアウトを短く（例 4s）**設定し、超過時はフォールバックで即 emit（デモが止まらないこと最優先）。

（Cloudflare Workers 側でロングポーリングを張らず、**Realtime 接続はブラウザ側**で行う。）

## 10. デモ台本（3分・プレゼンター用メモ）

1. 問題提起：「会議の沈黙は、合意とは限らない。」（5秒）
2. ファシリテーター画面を共有。デモソース再生開始。表面チャットは穏やかに同意が流れる。（〜30秒）
3. **山場**：場温計の「反論」だけが赤く上昇。「送信された言葉は穏やかなのに、送られなかった反論が溜まっています」。
4. **本物の証明**：別タブの参加者入力に、反論っぽい一文を打って消す。「**今のこの1通は、実際に AI がリアルタイムで分類しています**」→ 場温計が反応。
5. 穏やかな一文を打つと分類されても温度が上がらない（**素通しの実演**＝「常に書き換える/貼るだけのツールではない」証明）。
6. 提案発火：「反論の温度が上がっています。匿名で懸念を集めましょう」→ 次アクションへ。**ループを閉じて実用性を示す。**
7. プライバシー一言：「削除された本文は分類後すぐ破棄。個人は特定しません。」
